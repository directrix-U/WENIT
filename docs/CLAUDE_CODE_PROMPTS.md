# WENIT! — Claude Code 단계별 지시문

사용법: 각 Phase 지시문은 해당 단계에서만 사용한다. 먼저 Phase 0을 실행한다. Claude Code가 저장소를 분석하기 전에 전체 앱을 한 번에 재작성하도록 요청하지 않는다.

---

## 공통 시작 문구

아래 지시를 따르고 저장소 루트의 `CLAUDE.md`와 `WENIT_PROJECT_SPEC.md`(또는 `docs/WENIT_PROJECT_SPEC.md`)를 먼저 읽어라. 이 프로젝트에는 댓글/알림창 등 방해 요소가 있는 상황에서도 감지가 작동했던 실험 앱이 존재한다. 따라서 기존 구현과 검증 경험을 조사하지 않고 새 감지 로직을 덮어쓰지 마라. LLM을 숏폼 감지 판정에 사용하지 않는다. UI 원문·댓글·알림 원문·스크린샷은 저장하거나 전송하지 않는다. 실제로 빌드하고 테스트한 결과만 보고하라.

## Phase 0 — 저장소 감사(코드 수정 금지)

```text
먼저 프로젝트를 감사하라. 이번 단계에서는 코드를 수정하지 마라.

1. 저장소 구조, 언어, Android Gradle Plugin/Gradle/JDK/SDK 설정, 앱 진입점, 권한, 서비스, 저장소, 테스트 구조를 파악하라.
2. 기존 AccessibilityService/UsageStatsManager 및 감지 로직을 찾아 데이터 흐름을 추적하라. Shorts/Reels를 판정하는 조건, 이벤트 종류, 타이머, 댓글/알림창 예외처리, 세션 종료 처리를 요약하라.
3. 실제로 실행 가능한 빌드/테스트 명령을 찾아 실행하라. 실패하면 실패 원인을 구분해 보고하라.
4. 기존 테스트나 로그가 있으면 그것이 무엇을 증명하며 무엇을 증명하지 못하는지 설명하라.
5. YouTube UI 변경에 취약한 단일 view ID/문자열/좌표/아이콘 조건을 찾아 목록화하라. 코드와 테스트에서 확인할 수 없는 가정은 미확인으로 남겨라.
6. 기존 코드를 유지할 부분과 교체 후보를 나누고 최소 변경 계획을 제안하라.
7. Google Play Accessibility API 선언·사용자 고지·동의 정책 및 background Activity launch 제한을 출시 리스크로 보고하라. 정책 준수 여부를 단정하지 마라.

출력: 아키텍처 요약, 기존 detector의 흐름, 취약점 목록, 빌드/테스트 결과, 최소 수정 계획. 이번 단계에서는 파일을 수정하지 마라.
```

## Phase 1 — 감지 엔진 설계 및 분리

```text
Phase 0 감사 결과와 WENIT_PROJECT_SPEC.md를 바탕으로 감지 엔진을 분리하라. 기존에 정상 작동하던 동작을 회귀시키지 않는 것이 최우선이다.

요구사항:
- Platform event 수집, feature extraction, package별 adapter, state machine을 분리한다.
- 기존 스택에 합리적인 기반이 있으면 유지하고 대규모 재작성은 피한다.
- 최소 상태 OUTSIDE_TARGET, TARGET_FOREGROUND, CANDIDATE, SHORTFORM_ESTIMATED, TEMPORARILY_OBSCURED, EXIT_PENDING, ENDED를 표현한다. 이름은 기존 모델과 충돌하면 매핑하되 의미는 유지한다.
- null/empty/stale UI node와 미지원 이벤트를 정상적인 불확실 상태로 처리한다.
- UI 텍스트·댓글·알림 원문과 스크린샷은 로그에 남기지 않는다.
- 단일 이벤트/문자열/view ID만으로 숏폼을 확정하지 않는다.
- 상태 전이, grace period, duplicate events, event ordering, session resume에 단위 테스트를 추가한다.
- 실제 기기에서 측정하지 않은 시간 임계값은 설정 가능하게 두고 `TODO: VERIFY ON DEVICE`로 표시한다.

코드를 수정한 뒤 실행 가능한 빌드와 테스트를 실행하고, 결과를 보고하라. 테스트하지 않은 항목을 통과했다고 쓰지 마라.
```

## Phase 2 — 최신 YouTube Shorts 어댑터

```text
YouTube Shorts detector adapter를 집중적으로 다뤄라. 공통 엔진이나 다른 기능을 불필요하게 수정하지 마라.

1. 기존 규칙이 의존하는 text, contentDescription, view ID, node class, bounds, scroll/window events를 식별한다.
2. 특정 UI 문자열 또는 view ID 하나가 사라져도 바로 감지가 무너지지 않도록 구조 특징과 이벤트 시퀀스를 조합한다.
3. Clear Screen mode, 댓글 sheet, 알림 shade, 일반 긴 영상, 홈, 검색, 댓글창에서 거짓 확정하지 않는지 테스트한다.
4. 댓글·알림창이 열린 경우를 즉시 “숏폼 종료”로 보지 말고 일시 가림 상태를 사용한다. 단, 가려진 시간 전체를 확정 시청시간으로 무조건 더하지 마라.
5. 새로운 UI를 실제 기기에서 확인하지 못한 경우 “지원 완료”라고 표시하지 말고 필요한 수동 검증 항목을 제공한다.
6. 기존 정상 시나리오를 회귀 테스트로 유지하고 신규 시나리오를 추가한다.

마지막에 변경된 규칙, 신뢰 가능한 신호, 약한 신호, 미확인 상태, 실제 테스트 결과를 정리하라.
```

## Phase 3 — Instagram Reels 어댑터

```text
Instagram Reels를 별도 adapter로 구현하거나 기존 구현을 분리하라. YouTube 전용 규칙을 공통 detector에 넣지 마라.

Reels 피드와 일반 피드, DM, 댓글/공유 sheet, 알림 shade, 앱 전환, UI node를 얻지 못하는 상태를 구분한다. 실제 신호의 존재 여부는 기기에서 확인하고, 추측한 view ID나 문자열을 확정 규칙으로 만들지 마라. 불확실하면 unknown/candidate 상태로 남겨라.

공통 상태 머신과 기존 YouTube 테스트가 그대로 통과하는지 확인하라. 테스트를 실행하지 못했으면 정확한 이유를 보고하라.
```

## Phase 4 — 진단 로그와 ground-truth 테스트 도구

```text
감지 품질을 정량적으로 검증할 수 있는 내부 진단 기능을 구현하라.

- 로그는 event id, timestamp, package, detector version, state transition, reason code, 구조적 feature flags, confidence bucket만 포함한다.
- UI 원문 텍스트·댓글·DM·알림 내용·스크린샷은 저장하지 않는다.
- 개발용으로 테스트 구간을 시작/종료하고 사람이 정답 라벨(Shorts/Reels / non-short-form / obscured / unknown)을 지정할 수 있는 최소 기능을 만든다. 이 기능은 별도 debug build나 명확한 개발자 전용 화면에 둔다.
- precision, recall, false positives per hour, detection latency, state recovery rate를 계산하거나 내보내는 방법을 제공한다.
- 실제 라벨이 없는 경우 수치를 만들어내지 않는다. 숫자를 계산할 수 없으면 필요한 입력 형식과 계산 절차를 문서화한다.
- 테스트 fixture는 개인정보가 제거된 구조 요약만 포함한다.

테스트를 실행하고 실제 로그 예시(민감 정보 없음), 측정 가능한 지표, 아직 측정할 수 없는 지표를 보고하라.
```

## Phase 5 — 규칙 기반 알림 개입

```text
감지 엔진의 주요 회귀 테스트가 안정적으로 통과한 경우에만 규칙 기반 알림 개입을 추가하라. 이번 단계에서 LLM을 추가하지 마라.

- 사용자가 고른 대상 앱, 임계값, 적용 단위(연속 세션 또는 하루 누적), 쿨다운, 조용한 시간, 일시중지 설정을 구현한다.
- 임계값을 넘으면 알림 권한과 사용자 설정을 확인한 후 알림을 게시한다.
- 기본 흐름은 알림을 사용자가 탭해 앱 내 화면을 여는 방식이다. 백그라운드에서 Activity를 강제 실행하거나 권한·OS 제한을 우회하지 마라.
- 알림 권한/접근성 서비스/Usage access가 꺼져 있으면 현재 기능 상태를 정확히 표시한다.
- 세션당 중복 알림, 빠른 반복 알림, 앱 재시작 후 중복 알림을 방지한다.
- 알림을 받았음, 열었음, 사용자 피드백은 분리해 기록한다.
- “앱을 나갔다”를 곧바로 “도움이 됐다”로 간주하지 않는다.

단위 테스트와 주요 실기기 확인 목록을 추가하고 결과를 보고하라.
```

## Phase 6 — 목표·통계·피드백

```text
WENIT_PROJECT_SPEC.md의 MVP-C 범위만 구현하라. 캐릭터 성장·결제·소셜 기능은 추가하지 마라.

- 사용자가 하루/주간 목표를 설정하고 수정하거나 삭제할 수 있게 한다.
- 숏폼 추정 시간, 세션 수, 개입 수, 개입 후 행동 관측치, 주관적 도움 평가를 서로 다른 지표로 표시한다.
- “숏폼을 끊어낸 횟수”처럼 불확실한 의미를 가진 지표를 확정 성과처럼 표현하지 않는다.
- 로컬 데이터 전체 삭제와 저장 기간 설정을 제공한다.
- 빈 데이터·권한 부족·감지 불확실성을 정상 UI로 처리한다.

새 화면 및 저장소 테스트를 추가하고, 데이터 정의와 UI 표기가 일치하는지 확인하라.
```

## Phase 7 — AI 코치(나중 단계)

```text
감지/개입/로그가 안정되고 실제 파일럿 데이터가 확보된 경우에만 AI 코치의 최소 버전을 설계하라. 먼저 설계와 위협 모델을 제시하고, 사용자가 승인하기 전에는 API 호출을 구현하지 마라.

원칙:
- LLM 입력에는 원본 UI 트리, 댓글, DM, 알림 원문, 영상 내용, 스크린샷을 넣지 않는다.
- 사용자가 동의한 목표, 집계된 사용 통계, 명시적 피드백만 필요한 최소 범위에서 전달한다.
- LLM은 감지 여부, 임계값 판정, 권한, 시스템 설정, 자동 개입 실행을 제어하지 않는다.
- LLM이 실패하거나 지연되어도 로컬 규칙과 미리 검수된 문구로 작동한다.
- 행동과학/뇌과학 자료를 활용한다면 출처가 검수된 문서셋 또는 실제 검색-문맥주입-생성 구조의 RAG를 사용하고, 근거가 없을 때 의학적 주장을 만들어내지 않는다.
- 외부 API 전송 전에 별도 고지·동의, 전송 데이터 목록, 보관·삭제 정책을 설계한다.

우선 tool interface, 개인정보 경계, fallback, 테스트 계획을 제시하라. 불필요한 에이전트 프레임워크부터 도입하지 마라.
```

## UI가 다시 바뀌었을 때 쓰는 지시문

```text
YouTube/Instagram UI 변경으로 감지가 불안정해졌을 가능성이 있다. 바로 전체 detector를 재작성하지 마라.

1. 현재 앱 버전, Android 버전, 기기, detector version을 기록한다.
2. 기존 회귀 시나리오를 실행해 실패 사례를 reason code/state transition별로 분류한다.
3. 실패한 테스트에서 필요한 구조적 feature가 실제로 달라졌는지 확인한다. 확인할 수 없는 값은 추측하지 않는다.
4. 앱별 adapter만 최소 수정하고 공통 state machine은 꼭 필요한 경우가 아니면 건드리지 않는다.
5. 일반 영상/일반 피드 오탐, 댓글·알림 가림, UI node unavailable 테스트를 모두 재실행한다.
6. precision/recall을 계산할 라벨이 없다면 “개선됨”이라고 단정하지 말고 전후 테스트 결과만 보고한다.
7. 변경 내용, 실패했던 시나리오, 회귀 결과, 남은 한계를 정리한다.
```
